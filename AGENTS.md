# AGENTS.md — OpenAI Subscription for DSH

This repository builds **one independent, opt-in DSH Bundle**, not a package inside the DSH monorepo. Its public npm identity is `@h2mzzz/dsh-openai-subscription`, currently released as `0.1.3` on npmjs and GitHub Releases. Recommend npm package-name installation: published packages include prebuilt Host, Client, Typert, locale and Skill files and do not need Git prepare approval. Git source installation remains available through `prepare` and requires the consumer profile's build permission. The supported validation scope remains Ubuntu/Web: isolated Loader mount/unmount and registry installation have passed; authorized-account quota reads and the real Web quota UI have been checked, but full login/refresh/model end-to-end acceptance, Desktop and reset-card consumption remain incomplete. Read [README.md](README.md), [the release record](docs/RELEASE_NOTES_v0.1.3.md), [the implementation plan](docs/IMPLEMENTATION_PLAN.md), and [the pinned compatibility baseline](docs/COMPATIBILITY_BASELINE.md) before changing behavior.

## Branch naming and commit messages

- Name new branches `<type>/<short-description>`, for example `fix/windows-skill-path`, `feature/macos-support`, `refactor/auth-lifecycle`, or `add/platform-ci`. Use lowercase words separated by hyphens in the description. Choose `add`, `feature`, `fix`, or `refactor` according to the change; `docs`, `test`, and `chore` are also appropriate for their respective scopes. Do not use `codefix`, `codex`, or agent/tool names as branch prefixes.
- Apply the naming convention to future branches; rename existing local or remote branches only when explicitly requested by the user.
- Give each commit a concise title describing the concrete change, followed by a body of two or three sentences or short, separate bullet points. Explain the affected modules or behavior, the specific problems fixed and resulting behavior, and the relevant validation results. State material limitations or unrun checks when applicable. Describe the actual diff; avoid vague messages such as "fix issues" or "update code" and do not claim planned work as completed.

## Distribution and release documentation

- Keep package.json, both READMEs and the current release record aligned with each release. Preserve historical tags and release records; never overwrite a published npm version.
- Use npmjs as the public installation registry. GitHub Packages is a separate registry and does not mirror npmjs automatically. Keep the npm badge and package link in both READMEs.
- The release workflow is `.github/workflows/release.yml`: stable Release publication or manual dispatch validates the tag, runs package checks, publishes absent versions using npm OIDC, and downloads the actual registry package for Release attachments. Configure the matching npm trusted publisher before claiming automatic publishing works; YAML validation alone does not prove execution.
- Keep README focused on installation and user features. Put maintainers' build permissions, publishing, CI configuration and detailed verification records in docs, with links from README. Do not confuse cross-platform CI success with actual Desktop support.

## Target and ownership

- Target DSH `0.2.0-rc.2` at `639ed015397290b3745d163aafe02ffee4aa3f84` and its patched `@earendil-works/pi-ai@0.87.1`. Check a target release's actual APIs before claiming support for another version. `~/deepseek-harness` is the local reference checkout, **not** this repo's source tree or its command runner.
- Ship a single Bundle with a Cordis Host entry, a Web Client entry, `cordis.patch.yml`, and package-owned Typert artifacts. Host function entry named-exports `name`, `inject`, and `apply` (plus `Config` if needed), with **no default export**. The controller is a service-class plugin; the Client named-exports `inject` and `apply`. Declare required services and read genuinely optional ones with `ctx.get(name)`. Register slots, remotes, routes, listeners, and other resources within owning effects and prove disposal.
- Keep the provider route `codex-subscription`, settings-section ID, Remote namespace, and historical credential key `dsh-openai-subscription/codex` independent of the new **npm package name**. Never replace official DSH `openai`/`openai-codex`, edit its settings or `llm-pi-ai`, use another plugin's credentials, or change Desktop native code for this feature. Do not add this Bundle to DSH's shipped defaults.
- `dsh.client.inject` is package-level metadata, **not** a Cordis service dependency; runtime `inject` owns service ordering. Baseline browser modules (including React and `@deepseek-ai/dsh-client-ui-primitives`) are already supplied by DSH: do not redundantly list them in `dsh.client.external`. Use type-only imports for the settings slot contract and `ctx.slots.inject('settings.section', ...)` for the optional owner declaration.

## Security and behavior

- OAuth attempts, state/PKCE, callback, credential writes, token refresh, and quota requests belong to Host. Client/Remote receives only the minimum safe state and validated, actionable authorization links or device user code. Never send access/refresh tokens, authorization codes, full callback URLs, or credentials into Client, Session, logs, tests, screenshots, or demo artifacts. Do not silently fall back to environment API keys or Codex CLI credentials.
- Own login, refresh, cancel, timeout, sign-out, request abort, and unload as asynchronous lifecycles. Do not run concurrent writes to the same grant; release listeners, ports, timers, and requests, await teardown where necessary, and prevent callbacks after disposal. Contain notification errors; publish signed-in state or route changes only after the authoritative credential operation succeeds. Validate provider/network responses and Remote inputs at the trust boundary, not every statically typed local call.
- The plugin discovers the account-visible model catalog through Host; the installed pi-ai catalog is a static fallback, not a live entitlement lookup. Catalog visibility does not prove invocation entitlement: do not invent model IDs or claim account access without an actual request. For reasoning efforts, advertise only levels the model can send; Medium is the plugin default on models that support it, while the Web profile's chosen default model is a separate `agent-default-model` setting. Do not confuse per-request token usage with subscription quota. Missing limits/windows/reset times are unknown, never zero; a quota failure must not invalidate a working model login. Reset-card consumption requires a separate explicit user confirmation and an actual server-side result.
- Support text, ordinary tool calls, and catalog-declared user/tool image inputs through Host attachment conversion; real-account vision remains unverified. Reject unsupported inputs rather than silently dropping them. Keep README and API JSDoc aligned with what really works. A loopback callback page alone does not prove a successful token exchange or durable login, and a remote-browser/device-code fallback must not be described as verified until a real account confirms it.

## Web Client and verification

- Keep business data on Host. Use the typed locale dictionaries and DSH's derived `PropsRuntime<'settings.section'>`/`PropsLocale`/inject props; use existing primitives and `--dsw-*` semantic styling tokens. Test narrow layout, dark/light contrast, keyboard/focus behavior, disconnect/reconnect, and Desktop window chrome **before** claiming that platform supported. The local [UI judgment](.agents/skills/dsh-client-ui-ux/SKILL.md) and [async-test reliability](.agents/skills/dsh-ci-test-reliability/SKILL.md) skills apply to changes in those areas.
- Run the scripts **this repo actually defines**: `pnpm typecheck`, `pnpm test`, `pnpm test:package`, `npm pack --dry-run`, and `git diff --check`. The built-package smoke test and mocked lifecycle tests do **not** satisfy DSH's real Loader/profile-composition requirement: run that separately in an isolated profile, including disposal and route/slot/Remote removal, before release. If an authorized account is available, separately test actual login, refresh, model/tool calls, cancellation, and quota; report every skipped/unrun check honestly. GUI PRs need a privacy-reviewed recording of the real flow, not mock-only evidence.
- Manage installation via `dsh plugin --profile web ...` in a **separate DSH installation/test profile** where possible; this repo does not provide DSH-monorepo `pnpm` scripts. Never start/stop the user's Web service, migrate its installed package, or share OAuth artifacts without explicit authorization. An old unscoped package and the new scoped package must not be simultaneously enabled; preserve the credential key during migration.
- Do not commit credentials, real OAuth responses, or machine-specific profile data. Treat unfamiliar working-tree changes as user work. Before committing, inspect the diff and check the package contents as well as the tests.

The local `.agents/` skills are **selected copies**, not a substitute for the targeted DSH API.
